# ADR 0001. Выбор pure-Go драйвера SQLite

> **Статус:** принято, 2026-07-27.
> **Область:** серверная metadata DB (§6 `docs/tz/10-cloud-drive-spec.md`),
> все репозитории и миграция `0001`.
> **Закрывает:** первый пункт scope M12 «SQLite and migrations» (§25, M12,
> п. 1), который прямо требует ADR по pure-Go драйверу по критериям §6.1.
> **Решение:** `modernc.org/sqlite` v1.54.0; `github.com/ncruces/go-sqlite3` —
> заранее провалидированная запасная опция.

---

## 1. Статус

Принято. Заменяется только новым ADR. Все замеры ниже сняты на одном стенде
(Linux 7.0.0-28-generic x86_64, 4 CPU, 7.8 GiB RAM, Go 1.25.7, один SSD-раздел,
все сборки `CGO_ENABLED=0 -trimpath`). Переносить в решения следует **соотношения
между драйверами**, а не абсолютные числа: разброс между повторами на одиночных
commit'ах при `synchronous=NORMAL` достигал 20 % (1283 / 1550 / 1367 tps), по
max-latency — в разы (49 / 275 / 501 мс).

## 2. Контекст

> **О ссылках.** Ссылки на ТЗ даются номерами разделов
> (`docs/tz/10-cloud-drive-spec.md` §N.M), а не номерами строк: спецификация
> редактируется, и строчные якоря протухают молча. Формулировки требований
> цитируются дословно, чтобы их можно было найти поиском по тексту.

§6.1 фиксирует требования, которые драйвер обязан обеспечить, а не просто
«не мешать»:

| Требование §6.1 | Что это значит для драйвера |
|---|---|
| «SQLite работает в WAL mode» | `journal_mode=WAL` должен переживать открытие пула и не откатываться при реконнекте соединения |
| «`PRAGMA foreign_keys = ON` **на каждом соединении пула**», а не однократно | нужен механизм «PRAGMA при открытии соединения», а не `db.Exec` |
| «busy timeout настроен» | драйвер обязан реально ждать, а не возвращать `SQLITE_BUSY` мгновенно |
| «schema version хранится в `schema_migrations`» | обычный DDL, ограничений нет |
| «все миграции forward-only и выполняются до начала listener» | порядок открытия handle'ов и миграций фиксирован (см. §4.4) |
| «все timestamps в БД сервера — Unix epoch milliseconds UTC, тип `INTEGER`… RFC3339 в базе не хранится нигде» | нужен механический запрет на случайно забинденный `time.Time` |
| «repository methods принимают `context.Context`» | отмена контекста обязана прерывать выполняющийся запрос, а не только его ожидание |
| «Допустим pure-Go driver, чтобы сохранить `CGO_ENABLED=0`» | cgo-варианты выбывают |

Плюс шесть обязательных критериев выбора, перечисленных там же в §6.1 сразу за
требованием pure-Go: (1) поддерживаемые GOOS/GOARCH и кросс-компиляция без
C-тулчейна; (2) размер бинарника `fshare-daemon` до и после; (3) пропускная
способность и latency write-транзакции на профиле §24.5; (4) прирост
`go test -race ./...`; (5) работоспособность в `FROM scratch`; (6) поведение
`busy_timeout` и WAL под конкурентной записью. Нумерация критериев в этом ADR
соответствует порядку их перечисления в §6.1.

Отдельно — схема §6.3: семь
частичных индексов с `WHERE deleted_at_ms IS NULL / IS NOT NULL`, четыре
табличных `CHECK`, три FK с `ON DELETE RESTRICT`. Уникальность имени живого
ресурса держится **частичным** уникальным индексом `resources_uniq_name`
(§6.3) — без поддержки частичных индексов
soft-delete из §10.1 не работает вовсе.

Профиль нагрузки §24.5 читающий по
своей природе: 200 idle sessions, mixed 70/30 read/write, каталог на 1M записей
через пагинацию, журнальный polling 100 клиентов, slow client event queue. Из
снимаемых метрик драйвера напрямую касается «DB latency».

Целевая упаковка — существующий `Dockerfile:10` (`FROM scratch`), в образе нет
ни libc, ни `/etc`, ни shell.

### 3.2. Критерий: размер бинарника `fshare-daemon` до и после (§6.1, критерий 2)

«До» — реальный `cmd/fshare-daemon` текущего репозитория. «После» — его копия с
пакетом-обёрткой драйвера, **фактически вызываемым из достижимого кода**.

| Бинарник | Байт | vs «до» | `-s -w`, байт |
|---|---|---|---|
| fshare-daemon **до** | 5 146 462 | — | 3 444 920 |
| + glebarez | 11 299 160 | +6 152 698 (+120 %) | 7 561 400 |
| + **modernc** | 11 446 221 | **+6 299 759 (+122 %)** | 7 663 800 |
| + ncruces | 16 850 240 | **+11 703 778 (+227 %)** | 10 100 920 |

**Ловушка, найденная на практике.** Если драйвер только импортируется
(`_ "…"`) и нигде не вызывается, линкер выбрасывает у ncruces практически весь
SQLite:

| Программа | Байт | Прирост к «hello world» |
|---|---|---|
| `hello world` | 2 249 652 | — |
| + `_ "modernc.org/sqlite"` | 8 748 405 | +6 498 753 |
| + `_ "github.com/glebarez/go-sqlite"` | 8 700 164 | +6 450 512 |
| + `_ "github.com/ncruces/go-sqlite3/driver"` | 2 706 664 | **+457 012 — DCE съел SQLite** |

Проверено `go tool nm -size`: в реально работающем ncruces-бинарнике верхние
символы — `_sqlite3VdbeExec` (270 085 B), `_sqlite3RunParser` (187 930 B),
`_sqlite3Select` (140 650 B); в импорт-онли варианте их нет. Замер размера «по
импорту» даёт для ncruces цифру в 25 раз меньше реальной. Это прямо влияет на
PR1: если драйвер подключён, но ещё не вызван из достижимого кода, CI-метрика
размера скакнёт на 11 МБ в момент, когда repository-слой действительно заработает.

### 3.3. Критерий: пропускная способность и latency write-транзакции (§6.1, критерий 3)

Транзакция записи = `INSERT INTO resources` + `INSERT INTO changes`, то есть
мутация плюс журнальная запись (§14.1).
Схема — дословная §6.3. Три повтора для modernc/ncruces, один для glebarez.

**A. Bulk INSERT, 100 000 строк в одной транзакции, prepared statement**

|---|---|---|---|---|
| modernc | 22 657 | 19 751 | 20 679 | ~21 000 |
| ncruces | 20 000 | 19 971 | 19 927 | ~20 000 |

| glebarez | 258 | 3.88 | 4.71 | 8.60 | 66 |

**C. Одиночные commit'ы, `synchronous=NORMAL`** (штатный режим для WAL)

### 3.4. Критерий: прирост `go test -race ./...` (§6.1, критерий 4)

Базовая линия репозитория (11 пакетов, 48 файлов с тестами, драйвера SQLite нет),
кэши прогреты: `go test -count=1 ./...` — **13.59 с**; `go test -race -count=1
./...` — **17.88 с** (×1.32).

Репрезентативный repository-пакет: миграция всей схемы §6, засев 20 000 строк в
одной транзакции, 8 писателей × 200 write-tx + 8 читателей × 200 keyset-страниц,
проверка конфликта частичного UNIQUE:

| Пакет | `go test`, с | `go test -race`, с | замедление внутри теста |
|---|---|---|---|
| baseline без драйвера | 0.47 | 3.05 | ×9.9 |
| **ncruces** | 3.55 | **20.74** | **×8.6** |
| **modernc** | 2.83 | **36.82** | **×16.3** |
| **glebarez** | 4.89 | **64.48** | **×18.7** |

Пофазно (мс, без `-race` → с `-race`):

| Фаза | modernc | ncruces | glebarez |
|---|---|---|---|
| Миграция схемы | 58 → 266 | 55 → 48 | 19 → 175 |
| Засев 20 000 строк в tx | 794 → 19 798 (**×24.9**) | 930 → 9 864 (×10.6) | 2 076 → 45 468 (×21.9) |
| 8 писателей + 8 читателей | 1 230 → 14 660 (×11.9) | 1 151 → 8 597 (×7.5) | 1 174 → 16 093 (×13.7) |

Причина: modernc/glebarez — транслированный в Go код C-библиотеки, каждое
обращение к памяти инструментируется гонкодетектором. ncruces транслирован из
wasm и под `-race` вдвое дешевле.

**Проекция на CI:** один repository-пакет такой формы даёт **+35 с (modernc) /
+19 с (ncruces) / +62 с (glebarez)** на каждую цель матрицы; на четырёх целях —
**+2.3 / +1.2 / +4.1 минуты**.

### 3.5. Критерий: `FROM scratch` (§6.1, критерий 5)

| Проверка | modernc | ncruces | glebarez |
|---|---|---|---|
| `file` | statically linked | statically linked | statically linked |
| `ldd` | не динамический | не динамический | не динамический |
| `readelf -d` | динамической секции нет | нет | нет |

`strace -f` в пустом окружении (`env -i`), трассировка
`openat/open/readlink/statx/newfstatat/access/connect/socket/uname`, все пути вне
cwd:

| Драйвер | `/etc` | `.so` | `socket`/`connect` | Прочие внешние пути |
|---|---|---|---|---|
| modernc | **0** | **0** | **0** | `/dev/urandom` |
| ncruces | **0** | **0** | **0** | **нет вообще** |
| glebarez | **0** | **0** | **0** | `/dev/urandom` |

Всё остальное — сам файл БД и `-wal`/`-shm`/`-journal` рядом с ним.
Функционально: `sqlite=3.53.3 rows=1 journal=wal fk=1 busy=5000`.

**Не измерено:** реальный запуск в образе `FROM scratch` — демон Docker в среде
не поднят, `bwrap`/`unshare` заблокированы песочницей. Зависимости перечислены
через `strace`, что даёт тот же ответ по существу, но не является прогоном в
образе. Отсюда обязательное требование §6.3 (CI): smoke-тест `FROM scratch`.

**Оговорка про `/dev/urandom`:** modernc и glebarez его открывают. runc/containerd
создают `/dev/urandom` даже для `FROM scratch`, поэтому для Docker это не блокер,
но это жёсткая зависимость от того, что runtime предоставит `/dev`. Запуск в
chroot или initramfs без смонтированного `/dev` **не проверялся**.

### 3.6. Критерий: `busy_timeout` и WAL под конкурентной записью (§6.1, критерий 6)

**A. Горутины, 8 × 400 write-tx (пишущая с первого statement), пул 8**

| Драйвер | busy_timeout | ok | SQLITE_BUSY | tps | p99 мс | max мс |
|---|---|---|---|---|---|---|
| modernc | 0 | 457/3200 | **2743** | 1625 | 8.52 | 64 |
| modernc | 5000 | **3200/3200** | **0** | 1716 | 49.2 | 830 |
| ncruces | 0 | 598/3200 | **2602** | 654 | 3.34 | 501 |
| ncruces | 5000 | **3200/3200** | **0** | 1455 | 26.67 | 56 |
| glebarez | 0 | 477/3200 | **2723** | 1245 | 18.97 | 124 |
| glebarez | 5000 | **3200/3200** | **0** | 1545 | 79.81 | 931 |

**B. `busy_timeout` действительно ЖДЁТ.** Одно соединение удерживает write-lock
1500 мс, второе пытается писать:

| Драйвер | busy_timeout | Результат | Прождал |
|---|---|---|---|
| modernc | 0 | `database is locked (5) (SQLITE_BUSY)` | 2.2 мс |
| modernc | 3000 | успех | **1436 мс** |
| ncruces | 0 | `sqlite3: database is locked` | 3.3 мс |
| ncruces | 3000 | успех | **1402 мс** |
| glebarez | 0 | `database is locked (5) (SQLITE_BUSY)` | 1.7 мс |
| glebarez | 3000 | успех | **1436 мс** |

**C. Несколько ПРОЦЕССОВ, 8 ОС-процессов × 500 write-tx на один файл,
`busy_timeout=10000`:** у всех трёх **4000/4000 ok, 0 SQLITE_BUSY**; p99 —
modernc 34–80 мс, ncruces 21–27 мс, glebarez 9–61 мс. (В более раннем прогоне на
4 процессах ncruces дал 2 SQLITE_BUSY из 2000; на 8 процессах не воспроизвелось —
помечено как флак, не как систематика.)

**D. Главный результат: DEFERRED-транзакция, которая читает перед записью.**
8 горутин × 250 транзакций `BEGIN; SELECT …; INSERT …; COMMIT`,
`busy_timeout=5000` — то есть форма любой мутации §9 с проверкой конфликта имени
(§9):

| Драйвер | `_txlock` | ok | SQLITE_BUSY |
|---|---|---|---|
| modernc | deferred (по умолчанию) | **189/2000** | **1811** |
| modernc | **immediate** | **2000/2000** | **0** |
| ncruces | deferred | **436/2000** | **1564** |
| ncruces | **immediate** | **2000/2000** | **0** |
| glebarez | deferred | **266/2000** | **1734** |
| glebarez | **immediate** | **2000/2000** | **0** |

`busy_timeout` **не покрывает** `SQLITE_BUSY_SNAPSHOT` при апгрейде read-снапшота
до write-блокировки: 78–91 % транзакций мутации отваливаются. Это семантика
самого SQLite, идентичная у всех трёх драйверов, а не дефект драйвера.
`BEGIN IMMEDIATE` обязателен — см. §5.4.

**E. Топология пула** (modernc, реалистичная мутация §9: indexed lookup родителя +
проверка конфликта имени + INSERT resource + INSERT changes; 16 воркеров, 5 с,
каталог 100k):

| Конфигурация | read qps | read p99 мс | write tps | write p99 мс | отказов записи |
|---|---|---|---|---|---|
| A. один пул (8), BEGIN DEFERRED | 4898 | 10.02 | 454 | 17.73 | **8210** (`database is locked`) |
| B. один пул (8), `_txlock=immediate` | 1933 | 16.71 | **825** | 116.36 | **0** |
| C. раздельно: чтение `mode=ro` (8) + запись `immediate` (1) | 1414 | **2.63** | 604 | 135.74 | **0** |

B даёт максимальную суммарную пропускную способность, C — предсказуемый хвост
чтения (p99 2.63 мс против 16.71 мс), потому что читатели никогда не конкурируют
за пишущее соединение. Ни одна не выигрывает всухую.

### 3.7. Дополнительные проверки, общие для всех кандидатов

**PRAGMA на КАЖДОМ соединении пула (§6.1).**
8 одновременно удерживаемых `*sql.Conn`, на каждом PRAGMA читаются обратно:

| Способ | modernc | ncruces | glebarez |
|---|---|---|---|
| `_pragma=…` в DSN | **8/8** | **8/8** | **8/8** |
| однократный `db.Exec("PRAGMA foreign_keys = ON")` | **1/4** | 4/4 (\*) | **1/4** |

(\*) у ncruces 4/4 только потому, что его сборка SQLite имеет `foreign_keys`
включённым по умолчанию, а не потому что `Exec` размножился.

Значения по умолчанию при «голом» DSN без параметров:

| Драйвер | journal_mode | foreign_keys | busy_timeout | synchronous |
|---|---|---|---|---|
| modernc | delete | **0** | **0** | 2 (FULL) |
| ncruces | delete | 1 | 60000 | 2 (FULL) |
| glebarez | delete | **0** | 5000 | 2 (FULL) |

Вывод: путь через DSN — единственный работающий способ выполнить §6.1;
однократный `Exec` действует ровно на одно соединение, как §6.1 и предупреждает.

**Опечатка в DSN проглатывается молча — у всех трёх:**

| Что подсунуто | modernc | ncruces | glebarez |
|---|---|---|---|
| `_pragma=foreign_keys(1)` (верно) | fk=1 | fk=1 | fk=1 |
| `_pragma=foreign_keyz(1)` | **fk=0, ошибки нет** | (default 1) | **fk=0, ошибки нет** |
| `_pragmaa=foreign_keys(1)` | **fk=0, ошибки нет** | (default 1) | **fk=0, ошибки нет** |
| `_pragma=busy_timeout(abc)` | **fk=0, ошибки нет** | (default 1) | **fk=0, ошибки нет** |
| `_totally_unknown=42` | молча игнор | молча игнор | молча игнор |
| `_txlock=nonsense` | ошибка при первом использовании | ошибка при `sql.Open` | ошибка при первом использовании |

Валидируется только `_txlock`. Одна опечатка **тихо отключает ссылочную
целостность на всём проде**, и ни один тест этого не заметит, потому что
FK-нарушения просто перестанут отклоняться. Отсюда обязательная обратная вычитка
PRAGMA (§4.5).

**Поддержка `context.Context` (§6.1).** Тяжёлый
рекурсивный CTE, дедлайн 300 мс; BASELINE — то же выражение без дедлайна:

| Драйвер | BASELINE | `ExecContext` | `QueryRowContext` | `QueryContext`+`Next()` | текст ошибки |
|---|---|---|---|---|---|
| modernc | 77.7 с | **301 мс ✔** | **301 мс ✔** | **301 мс ✔** | `context deadline exceeded` |
| ncruces | 20.2 с | **300 мс ✔** | **301 мс ✔** | **301 мс ✔** | `sqlite3: interrupted` |
| glebarez | 7.35 с | 301 мс ✔ | **7.44 с ✘** | **7.47 с ✘** | `context deadline exceeded` (после полного выполнения) |

**У glebarez отмена контекста на пути запроса не работает:** `sqlite3_interrupt`
не вызывается, запрос отрабатывает целиком и только потом возвращает ошибку.

**Схема §6.3 и SQL-возможности** — работают у всех трёх, дословный DDL §6.3
создаётся без изменений: частичные уникальные индексы (дубль живого имени
отклонён; soft-delete + повторная вставка того же имени разрешена; две
soft-deleted строки с одинаковым именем разрешены — это ровно семантика §10.1),
FK-нарушение при `fk=1` отклонено, `STRICT` (включая всю схему §6.3 со всеми
`CHECK` и семью частичными индексами), `GENERATED ALWAYS AS … VIRTUAL/STORED`,
индекс по VIRTUAL-колонке, `RETURNING`, `SAVEPOINT`/`ROLLBACK TO`,
`PRAGMA wal_checkpoint(TRUNCATE)` через `database/sql`.

**`time.Time`, случайно забинденный в `INTEGER`-колонку `…_ms`:**

| Таблица | modernc | ncruces | glebarez |
|---|---|---|---|
| обычная rowid-таблица | **принято, typeof=text** | **принято, typeof=text** | **принято, typeof=text** |
| `STRICT` | **отклонено** (`cannot store TEXT value in INTEGER column`) | **отклонено** | **отклонено** |

То есть запрет §6.1 «RFC3339 в базе не хранится нигде»
(§6.1) без `STRICT` не имеет механического
обеспечения. См. §5.4.

## 4. Решение

### 4.1. Драйвер

**`modernc.org/sqlite` v1.54.0.**

Обоснование в одну фразу: профиль §24.5 читающий по своей природе — 200 idle
sessions, mixed 70/30, каталог на 1M записей через пагинацию, журнальный polling
100 клиентов, — и modernc выигрывает именно на read-пути (страница p99 5.9 против
9.5 мс, point lookup 37.8 против 51.5 мкс, `count(*)` 324 против 604 мс) при
вдвое меньшем приросте бинарника (+6.3 против +11.7 МБ). Цена — худший хвост
записи (mixed write p99 83 против 31 мс, max 752 против 65 мс) и вдвое более
дорогой `-race` (+35 против +19 с на цель).

**ncruces фиксируется как заранее провалидированная запасная опция.** Он отличается
только именем драйвера в `sql.Open` (`"sqlite3"` вместо `"sqlite"`) при идентичном
синтаксисе `_pragma` и `_txlock`; вся проверка §3 у него пройдена. Если хвост
latency записи станет ограничивающим фактором на §24.5, переключение — правка
двух строк в одном файле: импорт драйвера и его имя в `sql.Open` (§4.6, §5.5).

Версия пинится точно (`modernc.org/sqlite v1.54.0`). Апгрейд минорной версии —
обычный PR, но обязан прогнать проверки §6.

### 4.2. DSN

Два раздельных `*sql.DB` на один файл БД (топология C из §3.6.E). Ниже —
дословно проверенные строки (`cmd/dsnverify`, modernc v1.54.0).

**Пишущий handle:**

```text
file:{path}?_pragma=busy_timeout({database.busy_timeout_ms})&_pragma=foreign_keys(1)&_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)&_txlock=immediate
```

**Читающий handle:**

```text
file:{path}?_pragma=busy_timeout({database.busy_timeout_ms})&_pragma=foreign_keys(1)&_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)&mode=ro
```

`{database.busy_timeout_ms}` и значение `synchronous` подставляются из конфига
(§19.3), а не зашиваются в код: §6.1 требует сверять фактическое значение PRAGMA
с ожидаемым, поэтому у ожидаемого обязан быть единственный источник. Замеры ниже
сняты при `busy_timeout = 10000`, тогда как значение по умолчанию в §19.3 —
`5000`; на выводы это не влияет, потому что различие драйверов проявляется в
классе отказа (`SQLITE_BUSY_SNAPSHOT` не ретраится ни при каком таймауте), а не
в его длительности — см. §3.6.C.

Что именно проверено на этой паре:

- 8 одновременно удерживаемых `*sql.Conn` читающего handle и 1 пишущего:
  `journal_mode=wal`, `foreign_keys=1`, `busy_timeout=10000`, `synchronous=1` на
  КАЖДОМ, mismatching_conns = 0 — это и есть выполнение
  §6.1;
- `mode=ro` реально отклоняет запись: `attempt to write a readonly database (8)`;
- WAL не блокирует читателей: при открытой незакоммиченной write-транзакции
  читающий handle видит 1 строку, после commit — 2;
- `_txlock=immediate` убирает `SQLITE_BUSY` на read-then-write транзакциях
  полностью: 2000/2000 против 189/2000 при deferred.

**Разделение PRAGMA по области действия:**

| PRAGMA | Область | Как обеспечивается |
|---|---|---|
| `busy_timeout({database.busy_timeout_ms})` | **на соединение** | `_pragma` в DSN обоих handle |
| `foreign_keys(1)` | **на соединение** | `_pragma` в DSN обоих handle |
| `synchronous(NORMAL)` | **на соединение** | `_pragma` в DSN обоих handle |
| `journal_mode(WAL)` | **на файл БД**, персистентно в заголовке | `_pragma` в DSN всё равно указывается: идемпотентно, и даёт fail-fast, если файл кем-то переведён обратно в `delete` |
| `_txlock=immediate` | параметр драйвера, не PRAGMA: форма `BEGIN` | только пишущий handle |
| `mode=ro` | параметр открытия файла | только читающий handle |

`PRAGMA` через `db.Exec` при работающем пуле **запрещён**: замер даёт 1/4
соединений с нужным значением (§3.7). Единственное исключение — явно
запрошенный `PRAGMA wal_checkpoint(TRUNCATE)` на пишущем handle (пул = 1
соединение, значит соединение ровно одно).

**Порядок параметров.** modernc сортирует список `_pragma` так, что
`busy_timeout` применяется первым (`modernc.org/sqlite@v1.54.0/sqlite.go:225-228`).
Это важно: переключение `journal_mode` на WAL само по себе может упереться в
блокировку, и без уже установленного `busy_timeout` открытие соединения падало
бы. Полагаться на это как на контракт не стоит (потому и обязательна вычитка
§4.5), но переставлять параметры местами не нужно.

**Чего в DSN быть не должно.** `_time_format`, `_time_integer_format`,
`_timezone`, `_inttotime`, `_texttotime` — не нужны: §6.1 хранит все временные
метки как `INTEGER` unix-миллисекунды в колонках `_ms`, и `time.Time` в запросы
не биндится вообще. Механическую защиту даёт `STRICT` (§5.4), а не DSN.

### 4.3. `synchronous=NORMAL` — осознанное решение, а не наследие примера

`NORMAL` против `FULL`: **1283–1550 tps против 244–261 tps** на одиночных
commit'ах, разница ровно в 5 раз (§3.3 B и C).

`NORMAL` при WAL защищает от падения процесса (краш демона потери
закоммиченных данных не даёт), но допускает потерю последних коммитов при отказе
ОС или питания. Этот сценарий закрывают startup reconciliation и recovery marker
§5.5 (в том числе требование «выполняется до открытия
listener»): при старте расхождение метаданных и ФС
детектируется и устраняется, а незавершённая операция доигрывается или
откатывается по маркеру. Поэтому пятикратная пропускная способность выбрана
осознанно.

Если позже появится требование «ни один подтверждённый commit не теряется при
отказе питания без reconciliation», значение меняется на `FULL` в одном месте, с
ожидаемой ценой ×5 по write tps — и это отдельное изменение ADR, а не настройка
конфига.

### 4.4. Настройки пула `database/sql` и порядок открытия

SQLite допускает **ровно одного писателя** на файл БД — это свойство движка, а не
драйвера. Пул из N пишущих соединений не увеличивает пропускную способность
записи, а превращает конкуренцию за write-lock в очередь внутри SQLite с
непредсказуемым хвостом (§3.6 A: `max` 830 мс у modernc при пуле 8). Поэтому:

| Handle | `SetMaxOpenConns` | `SetMaxIdleConns` | `SetConnMaxLifetime` | Почему |
|---|---|---|---|---|
| пишущий | **1** | **1** | **0** (без ограничения) | один писатель у SQLite физически; очередь на write держит `database/sql`, а не блокировки SQLite. Idle = 1, чтобы соединение не пересоздавалось и не переприменяло PRAGMA на каждой транзакции. Lifetime 0: пересоздание соединения бессмысленно (нет сети, нет сервера, который рвёт коннект) и лишь роняет прогретый page cache |
| читающий | **N** = число параллельных читателей (базово **8**) | **N** | **0** | WAL даёт снапшотное чтение без блокировки писателя (проверено, §4.2); N = 8 — значение, на котором сняты все замеры. Idle = Max, чтобы соединения не закрывались между всплесками журнального polling |

`N` конфигурируемо; разумный дефолт — `max(4, GOMAXPROCS)`, но CI и нагрузочные
цифры §24.5 снимаются на 8.

**Обоснование выбора топологии C (раздельные handle), а не B (единый пул с
`_txlock=immediate`).** Замер §3.6.E: B даёт 825 write tps против 604, C даёт
read p99 **2.63 мс против 16.71 мс**. Профиль §24.5 — 200 idle sessions,
journal polling 100 клиентов, slow client event queue — упирается в
предсказуемость хвоста чтения, а не в суммарную запись; из снимаемых метрик
§24.5 названа «DB latency». Выбрана C. Решение переоценивается, если реальный
профиль окажется пишущим — тогда B, с одной точкой правки в конструкторе.

**Порядок открытия фиксирован** (следствие `mode=ro`: он не создаёт файл БД и не
может создать WAL):

1. открыть **пишущий** handle;
2. прогнать forward-only миграции, включая `0001`
   (§6.1, «выполняются до начала listener»);
3. выполнить обратную вычитку PRAGMA (§4.5) на пишущем handle;
4. открыть **читающий** handle и выполнить обратную вычитку PRAGMA на нём, взяв
   `N` соединений одновременно;
5. только теперь — startup reconciliation §5.5 и открытие listener.

### 4.5. Обязательная обратная вычитка PRAGMA (fail-fast)

Драйвер **молча** проглатывает любую опечатку в DSN (§3.7): `_pragma=foreign_keyz(1)`,
`_pragmaa=…`, `_pragma=busy_timeout(abc)`, неизвестные параметры — ни ошибки, ни
предупреждения, при этом `foreign_keys` остаётся 0. Валидируется только `_txlock`.

Поэтому после `sql.Open` реализация **обязана**: взять соединение через
`db.Conn(ctx)` (для читающего handle — все `N` одновременно), прочитать
`PRAGMA journal_mode`, `PRAGMA foreign_keys`, `PRAGMA busy_timeout`,
`PRAGMA synchronous`, сверить с ожидаемыми (`wal`, `1`, `database.busy_timeout_ms`, `database.synchronous`) и **упасть
при любом расхождении**, назвав конкретный PRAGMA, ожидаемое и фактическое
значение. Без этой проверки одна опечатка тихо отключает ссылочную целостность на
всём проде, и ни один тест этого не заметит, потому что FK-нарушения просто
перестанут отклоняться.

### 4.6. Слой изоляции

Repository-слой работает **только через `database/sql`**. Драйверо-специфичный
импорт (`_ "modernc.org/sqlite"`) и строка имени драйвера в `sql.Open` живут
ровно в одном файле — конструкторе пары handle'ов (предлагается
`internal/db/sqlite.go`; точное имя пакета — вопрос PR1, см. §26, пример M12).
Ни один пакет репозиториев, сервисов или
миграций не вправе импортировать драйвер.

Запрет проверяется механически в CI (§6.5): импорт драйвера вне разрешённого
файла — красная сборка. Именно этот запрет делает переключение на ncruces правкой
двух строк (импорт + `"sqlite"` → `"sqlite3"`).

## 5. Последствия

### 5.1. Размер бинарника и Dockerfile

`fshare-daemon` растёт с 5 146 462 до **11 446 221 байт (+6.3 МБ, +122 %)**;
со `-s -w` — 3 444 920 → 7 663 800. Для образа `FROM scratch` (`Dockerfile:10`)
это единственная статья роста: внешних `.so` не добавляется, `/etc` не требуется
(§3.5).

Dockerfile меняется в двух местах:

- в образ добавляется каталог для файла БД и WAL/SHM рядом с ним; `/data`
  уже bind-mount, отдельного volume не требуется, но БД обязана лежать на
  файловой системе с рабочим `fcntl`-локом (не на сетевой ФС);
- `FROM scratch` сохраняется; **строка `CGO_ENABLED=0` в `Dockerfile:8` теперь
  несёт функциональную нагрузку, а не только гигиеническую** — её удаление даст
  собирающийся бинарник, который потащит динамическую линковку.

Помнить про `/dev/urandom`: modernc его открывает. runc/containerd предоставляют
`/dev` даже для `FROM scratch`, поэтому в Docker это не блокер; для chroot или
initramfs без `/dev` поведение **не проверялось**.

### 5.2. Время сборки и тестов, CI

- `go test -race ./...` сегодня — 17.88 с. Один repository-пакет формы §3.4
  добавляет **+35 с на каждую цель матрицы**; текущая матрица `ci.yml` —
  ubuntu/windows/macos, то есть **+1.7 минуты**, а на матрице из четырёх целей —
  **+2.3 минуты**.
- Решение: `-race` остаётся на всей матрице, пока суммарное время job'а не
  превысит ~5 минут. Если repository-тестов станет много, `-race` сужается до
  `linux/amd64`, а остальные цели гоняют `go test` без него — это дешевле, чем
  терять покрытие гонок совсем. Явный триггер пересмотра: `go test -race ./...`
  дольше 5 минут на ubuntu-latest.
- Кросс-компиляция: job `cross-compile` в `ci.yml` покрывает три цели из четырёх
  обязательных; **добавляется `linux/arm64`** (§6.1).
- Сборка: прирост времени компиляции заметен только на холодном кэше модулей;
  `modernc.org/libc` v1.74.1 — крупная зависимость, её стоит держать в
  `actions/setup-go` кэше.
- Замечание по среде: в песочнице разработки `proxy.golang.org` отдаёт zip-архивы
  редиректом на `storage.googleapis.com`, который недоступен, и `go get` для новых
  модулей падает с `EOF`; обход — `GOPROXY=https://goproxy.cn,direct`. Для CI это
  отдельный вопрос (GitHub-раннеры проблемы не имеют), но при появлении
  self-hosted раннера про это надо помнить.

### 5.3. Метрика размера бинарника в CI ненадёжна до PR2

Если в PR1 драйвер подключён, но ещё не вызван из достижимого кода, DCE выбросит
почти весь SQLite и замер даст ложно оптимистичную цифру (для ncruces — в 25 раз
меньше реальной, §3.2). Порог размера в CI имеет смысл включать **после** того,
как repository-слой действительно работает; до тех пор метрика информационная.

### 5.4. Уточнения спецификации, внесённые этим ADR в §6.1

Три пункта, которые обязана выполнять реализация. Все три выведены замерами §3,
в исходной редакции §6.1 отсутствовали и внесены в неё тем же коммитом, что и
настоящий ADR, — отдельного PR документации они не требуют:

1. **`BEGIN IMMEDIATE` для всех write-транзакций.** §6.1 требует «busy timeout
   настроен» (§6.1), но этого доказуемо
   недостаточно: при DEFERRED-транзакции, которая читает перед записью (то есть
   при любой мутации §9 с проверкой конфликта имени), `busy_timeout=5000` спасает
   189–436 транзакций из 2000, остальные падают с `SQLITE_BUSY_SNAPSHOT`, который
   `busy_timeout` принципиально не ретраит. С `_txlock=immediate` — 2000/2000 у
   всех трёх драйверов. Реализация по букве текущего §6.1 будет разваливаться под
   конкуренцией.
2. **Таблицы §6 объявляются `STRICT`.** Запрет §6.1 «RFC3339 в базе не хранится
   нигде» (§6.1) без `STRICT` не имеет
   механического обеспечения: случайно забинденный `time.Time` молча ложится
   TEXT-строкой в `INTEGER`-колонку `_ms` у всех трёх драйверов. Проверено, что
   вся схема §6.3 со всеми `CHECK` и семью частичными индексами создаётся как
   `STRICT`, и что `STRICT` такой bind отклоняет (`cannot store TEXT value in
   INTEGER column`). Миграция `0001` пишется сразу со `STRICT` — форматом файла
   это не меняется, но задним числом добавить `STRICT` в существующую таблицу
   нельзя без пересоздания.
3. **Обратная вычитка PRAGMA после открытия** (§4.5) — как явное требование §6.1,
   а не как деталь реализации.

Все три сегодня присутствуют в §6.1 списком требований: «каждая транзакция,
способная выполнить запись, открывается как `BEGIN IMMEDIATE`», «все таблицы
раздела 6 объявлены `STRICT`» и «фактические значения PRAGMA вычитываются
обратно после открытия каждого соединения и сверяются с ожидаемыми».

### 5.5. Если драйвер придётся менять

Изолирующий слой — один файл с импортом драйвера и именем в `sql.Open` (§4.6).
Переход на ncruces: заменить импорт на
`_ "github.com/ncruces/go-sqlite3/driver"` (и **не** импортировать
`…/go-sqlite3/embed` — он больше не нужен и печатает предупреждение в stderr),
поменять `"sqlite"` на `"sqlite3"`. DSN, синтаксис `_pragma`, `_txlock` и вся
топология пула не меняются — проверено. Ожидаемая дельта: запись быстрее и с
коротким хвостом, чтение в 1.5–1.9× медленнее, бинарник +5.4 МБ, `-race` вдвое
дешевле.

Ограничение на будущее: modernc и glebarez регистрируют одно и то же имя
драйвера `"sqlite"`, поэтому одновременная линковка обоих невозможна (паника при
`init`). Сравнительный прогон двух драйверов в одном процессе (например, в
migration-тесте) достижим только для пары modernc + ncruces.

### 5.6. Известные риски выбранного драйвера

- **Хвост latency записи.** Под mixed 70/30 write p99 83 мс против 31 мс у
  ncruces, max 752 мс против 65 мс — длинный хвост даёт WAL checkpoint,
  попадающий в commit. Для §24.5, где снимается «DB latency», это может стать
  ограничивающим фактором. Смягчение — настройка `wal_autocheckpoint` и/или
  вынос checkpoint в отдельный фоновый цикл; **в замерах не проверялось**. Если
  не помогает — переход на ncruces по §5.5.
- **Абсолютные числа привязаны к стенду** (§1); в решениях использовать
  соотношения.
- **`FROM scratch` проверен косвенно** (§3.5) — отсюда обязательный smoke-тест
  §6.3.

## 6. Как проверять

Проверки, которые обязаны попасть в CI (`.github/workflows/ci.yml`). Каждая
привязана к критерию §6.1.

### 6.1. Сборка под четыре обязательные платформы с `CGO_ENABLED=0` (§6.1, критерий 1)

Job `cross-compile` расширяется до четырёх обязательных целей; `CGO_ENABLED=0`
указывается явно, чтобы цель не начала зависеть от значения по умолчанию на
раннере:

```yaml
- run: CGO_ENABLED=0 GOOS=linux   GOARCH=amd64 go build ./...
- run: CGO_ENABLED=0 GOOS=linux   GOARCH=arm64 go build ./...
- run: CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./...
- run: CGO_ENABLED=0 GOOS=darwin  GOARCH=arm64 go build ./...
```

Плюс проверка, что cgo не просочился в граф зависимостей (защита от повторения
истории с mattn, который при `CGO_ENABLED=0` собирается и падает только в
рантайме):

```yaml
- run: |
    if CGO_ENABLED=0 go list -deps ./cmd/fshare-daemon | grep -qx 'runtime/cgo'; then
      echo "runtime/cgo в графе зависимостей демона"; exit 1
    fi
```

### 6.2. Отсутствие динамических зависимостей (§6.1, критерий 5)

На ubuntu-раннере после сборки демона:

```yaml
- run: CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o /tmp/fshare-daemon ./cmd/fshare-daemon
- run: |
    file /tmp/fshare-daemon | grep -q 'statically linked' || { echo "не статический"; exit 1; }
    ! readelf -d /tmp/fshare-daemon | grep -q 'NEEDED' || { echo "есть NEEDED"; exit 1; }
    ! ldd /tmp/fshare-daemon 2>&1 | grep -q '=>'      || { echo "есть .so"; exit 1; }
```

### 6.3. Smoke-тест реального образа `FROM scratch` (§6.1, критерий 5)

То, что в исследовании заменено на `strace` и **не** проверено прогоном в образе
(§3.5). В CI:

```yaml
- run: docker build -t fshare-daemon:ci .
- run: |
    docker run --rm -v "$PWD/ci-data:/data" fshare-daemon:ci --migrate-only
```

Критерий прохождения: контейнер завершается с кодом 0, в `ci-data` появились файл
БД и `-wal`, `schema_migrations` содержит версию `1`. Форма подкоманды
(`--migrate-only` или эквивалент) определяется в PR1 вместе с миграцией `0001`.

### 6.4. Go-тесты (пакет `internal/db`), обязательные

1. **Конкурентная запись с `busy_timeout` и `BEGIN IMMEDIATE`** (§6.1, «busy timeout настроен», §6.1, критерий 6)
   — главный тест: 8 горутин × 250 транзакций вида
   `BEGIN IMMEDIATE; SELECT (проверка конфликта имени); INSERT resources; INSERT changes; COMMIT`.
   Критерий: **2000/2000 ok, ноль `SQLITE_BUSY`**. Замер: с `_txlock=immediate` —
   2000/2000; при deferred — 189/2000. Тест обязан падать, если кто-то уберёт
   `_txlock=immediate` из DSN.
2. **`busy_timeout` действительно ждёт** (§6.1, «busy timeout настроен»): одно соединение удерживает
   write-lock 1500 мс, второе пишет и обязано дождаться (~1.4 с) и завершиться
   успешно, а не вернуть `SQLITE_BUSY` за 2 мс.
3. **PRAGMA на КАЖДОМ соединении пула** (§6.1, «PRAGMA foreign_keys = ON на каждом соединении пула»): взять `N`=8 соединений
   читающего handle и 1 пишущего одновременно, на каждом прочитать
   `journal_mode`/`foreign_keys`/`busy_timeout`/`synchronous`, требовать
   `wal`/`1`/`database.busy_timeout_ms`/`database.synchronous` на всех. Критерий: mismatching_conns = 0.
4. **Fail-fast на опечатку в DSN** (§4.5): конструктор, которому подсунут
   `_pragma=foreign_keyz(1)` или `_pragmaa=…`, обязан вернуть ошибку. Негативный
   тест: без вычитки драйвер молча оставляет `foreign_keys=0`.
5. **`mode=ro` действительно read-only**: запись через читающий handle обязана
   дать `attempt to write a readonly database (8)`.
6. **WAL не блокирует читателей**: при открытой незакоммиченной write-транзакции
   читающий handle видит прежнее состояние, после commit — новое.
7. **Отмена `context.Context` прерывает запрос** (§6.1, «repository methods принимают context.Context»): тяжёлый рекурсивный
   CTE с дедлайном 300 мс обязан вернуть `context deadline exceeded` за ~300 мс,
   а не за время полного выполнения. Тест дисквалифицирует glebarez, если кто-то
   решит вернуться к нему.
8. **Схема §6.3 и `STRICT`**: миграция `0001` создаёт все таблицы; дубль живого
   имени отклоняется `resources_uniq_name`; soft-delete + повторная вставка того
   же имени разрешена; две soft-deleted строки с одинаковым именем разрешены;
   FK-нарушение отклоняется при `fk=1`; bind `time.Time` в колонку `_ms`
   отклоняется (`cannot store TEXT value in INTEGER column`).
9. **Миграции forward-only до listener** (§6.1, «все миграции forward-only и выполняются до начала listener»): миграции применяются на
   свежем файле, повторный запуск — no-op, `schema_migrations` монотонна;
   попытка открыть читающий handle до миграции (файла БД нет) — ожидаемая ошибка,
   а не тихое создание пустой БД.

### 6.5. Запрет драйверо-специфичных импортов (§4.6)

```yaml
- run: |
    hits=$(grep -rln 'modernc.org/sqlite' --include='*.go' . | grep -v '^./internal/db/sqlite.go$' || true)
    if [ -n "$hits" ]; then echo "импорт драйвера вне internal/db/sqlite.go:"; echo "$hits"; exit 1; fi
```

### 6.6. Информационные метрики (не gate до PR2)

- размер `fshare-daemon` для linux/amd64 — печатается в лог job'а; порог
  (ориентир: 13 МБ при измеренных 11.45 МБ) включается после того, как драйвер
  вызывается из достижимого кода (§5.3);
- время `go test -race ./...` — печатается, триггер пересмотра матрицы из §5.2.

### 6.7. Не покрывается CI (осознанно)

- нагрузочные сценарии §24.5 (каталог 1M, mixed 70/30, 200 idle sessions) — это
  отдельный прогон, не PR-gate;
- запуск в chroot/initramfs без смонтированного `/dev` (зависимость modernc от
  `/dev/urandom`) — проверяется только если такой сценарий развёртывания
  появится.
