# 07. Перспектива: пользователи, роли, квоты («мини-Яндекс.Диск»)

Этот документ — **проектный задел** (этапы M12–M13), не обязательства v2.0.
Цель: зафиксировать целевую модель сейчас, чтобы решения v2.0 ей не противоречили.

> **Статус: исторический.** Целевая модель переописана заново и подробно в
> [10-cloud-drive-spec.md](10-cloud-drive-spec.md) (этапы M12–M18). Текст ниже
> сохраняется как история решения; там, где он расходится с документом 10,
> нормативен документ 10 — расхождения помечены врезками в начале разделов.

## 1. Модель данных

> **Устарело.** Заменено [10-cloud-drive-spec.md](10-cloud-drive-spec.md) §6.2
> (таблица `users`), §7.1 (роли) и §21.4 (миграция `users.json`). Изменилось:
> ролей остаётся ровно две — `user` и `admin` (`uploader`/`readonly` отменены,
> точечные права выражаются ACL из §7.3, M16), флаг `enabled` заменён
> трёхзначным `users.state` (`active`/`disabled`/`pending_delete`), а отдельных
> сущностей `Space` и `Grant` не заводится: квота живёт колонками
> `quota_bytes`/`used_bytes`/`reserved_bytes` той же таблицы `users`.

```
User:   id · login · pass (Argon2id/verifier) · role · enabled · created_at
Role:   admin | user           (v2.0)
        + uploader | readonly  (M12: гранулярность)
Space:  user_id · quota_bytes · used_bytes
Grant:  user_id · vpath · rights (r / rw)     (M12: шаринг между пользователями)
```

Хранилище: `users.json` → **SQLite** на этапе M12 (транзакционность нужна квотам:
`used_bytes` должен обновляться атомарно с окончанием записи файла).

## 2. Пространства и изоляция

> **Устарело.** Раскладку на диске и виртуальные корни задают
> [10-cloud-drive-spec.md](10-cloud-drive-spec.md) §5.1 (data root) и §7.2
> (virtual roots). Изменилось: корней ровно два — `/home` и `/public`, корня
> `/shared` нет (обмен между пользователями — публичные ссылки §17 и ACL §7.3),
> home адресуется по `UserID`, а не по логину (`files/users/<UserID>/live`),
> содержимое лежит ID-адресуемо (`live/<aa>/<bb>/<resource-id>`), а изоляцию
> обеспечивает отдельный `os.Root` на сессию — обслуживать аутентифицированную
> сессию поверх общего VFS запрещено. Сам принцип «изоляция на сервере, а не
> скрытием в UI» сохранён и распространён на v2-сессии.

Плоская модель «один share-root для всех» превращается в:

```
/srv/fileshare/
├── public/            # видно всем (то, что раздаётся сейчас)
├── homes/
│   ├── vit/           # личное пространство: квота, полный доступ владельца
│   └── anna/
└── shared/            # M12+: каталоги, расшаренные грантами
```

Виртуальный корень зависит от пользователя — VFS монтирует:

```
/ ─┬─ public   → /srv/fileshare/public      (r для всех)
   ├─ home     → /srv/fileshare/homes/<login>  (rw владельцу, невидим другим)
   └─ shared/… → по таблице Grant
```

**Изоляция обеспечивается на сервере** (VFS не отдаст чужой `home` ни при каком
пути — проверка на этапе `resolve`), а не «скрытием» в UI. Это прямой ответ на
требование «чтобы пользователи между собой не перепрыгивали».

## 3. Квоты

> **Устарело частично.** Учёт квоты задают
> [10-cloud-drive-spec.md](10-cloud-drive-spec.md) §11.4 (формулы `used_bytes` и
> `reserved_bytes`) и §8.2 (проверка на `UPLOAD_BEGIN`). Изменилось: отказ до
> передачи байт сохранён, но выполняется через резервирование места
> (`reserved_bytes`), а не сверкой `used + size`, и учитывает сохраняемую версию
> затираемого файла; per-role rate-лимитов не будет — §19.3 знает только
> `limits.per_client_bps` и `limits.global_bps`, ключа `limits.roles.*` в
> конфиге нет. Полоса квоты в TUI остаётся и приезжает вместе с
> `QUOTA_REQUEST`/`QUOTA_RESPONSE` на этапе M13 (§25).

- Квота — на `home` пользователя (байты). Проверка **до** начала upload:
  `UPLOAD_REQUEST(size)` → сервер сверяет `used + size ≤ quota` →
  `QUOTA_EXCEEDED` сразу, а не после передачи гигабайта.
- `used_bytes` пересчитывается фоновым обходом при старте (self-healing) и
  инкрементально поддерживается на каждой записи/удалении.
- В клиенте: полоска квоты в статусе панели `home` (`▓▓▓░░ 6.2G / 10G`),
  жёлтая при > 80%, красная при > 95%.
- Rate-лимиты тоже становятся per-role/per-user (таблица в конфиге:
  `limits.roles.user.per_client_bps`).

## 4. Upload (без него квоты бессмысленны)

> **Устарело.** Upload задан заново:
> [10-cloud-drive-spec.md](10-cloud-drive-spec.md) §8 (state machine
> begin → chunks → commit), номера опкодов — §3.8. Изменилось:
> распределение `UPLOAD_*` в группу `0x3x` отменено — эти коды заняты
> `DOWNLOAD_*` (`internal/proto/proto.go:72-76`), сообщения переехали в
> `0x70–0x7F` протокола v3; вместо `UPLOAD_DONE(checksum) → UPLOAD_RESULT` —
> `UPLOAD_COMMIT`/`UPLOAD_DONE` с возобновлением по `client_upload_key` и
> `UPLOAD_STATUS`, а `.upart` заменён staging-каталогом с atomic publish и
> recovery-маркером (§5.4).

Зеркально download'у, протокол зарезервирован в группе `0x3x`:

```
UPLOAD_REQUEST (path, size, mtime)  → UPLOAD_ACCEPT (transfer_id, offset)
                                       // offset > 0 = докачка недозалитого
UPLOAD_CHUNK   (transfer_id, bytes) → …
UPLOAD_DONE    (transfer_id, checksum) → UPLOAD_RESULT (ok / checksum mismatch)
```

- Сервер пишет во временный файл (`.upart`), переименовывает после сверки
  checksum — на диске никогда не бывает «наполовину залитых» файлов под финальным
  именем.
- В TUI: F5 с локальной панели на удалённую `home` — полная симметрия с download,
  F6 — переместить, F7 — mkdir, F8 — удалить (в пределах прав).

## 5. Администрирование пользователей (M12, вкладка в админ-панели)

> **Устарело.** Администрирование пользователей задано заново:
> [10-cloud-drive-spec.md](10-cloud-drive-spec.md) §7.4 (набор команд
> `user add/list/passwd/role/quota/disable/enable/delete/purge` и таблица
> «операция → сессии → токены → shares»), номера опкодов — §3.8. Изменилось:
> диапазон `0x5A–0x5F` под `ADMIN_USER_*` отменён — он конфликтует с уже
> реализованными `ADMIN_SHUTDOWN`/`ADMIN_RELOAD_USERS`
> (`internal/proto/proto.go:95-98`); сообщения переехали в `0xC0–0xCD`, и
> отдельного опкода на каждую команду нет: `ADMIN_USER_MODIFY_REQUEST` несёт
> поле-дискриминатор `Action`, `ADMIN_USER_DELETE_REQUEST` — поле `Mode`. Аудит
> сохранён (§20.2), добавлены инвариант последнего администратора
> (`LAST_ADMIN_REQUIRED`) и двухфазное удаление через `pending_delete`.

`ADMIN_USER_*` сообщения (`0x5A–0x5F`): list / add / disable / set-role /
set-quota / reset-password. Всё через тот же AdminService с аудитом.

## 6. Что для этого уже заложено в v2.0 (чтобы потом не переделывать)

> **Устарело частично.** Первые три пункта в силе: `Role` расширяется без слома
> формата (`internal/proto/proto.go:170-172`), `transfer_id` есть в передачах,
> код `QUOTA_EXCEEDED = 13` зарезервирован (`internal/proto/proto.go:246`).
> Последние два пункта заменены [10-cloud-drive-spec.md](10-cloud-drive-spec.md)
> §7.2 и §7.3: «подмена одного корня на маунты в одном классе VFS» не состоится
> — источником истины о дереве становится таблица `resources` (§6.3, инвариант
> 14), а изоляцию даёт per-session `os.Root`; фильтрация событий по подписке
> недостаточна — событие рендерится и кодируется отдельно под каждого
> получателя, единый пред-кодированный broadcast-кадр запрещён, а невидимое
> получателю событие не отправляется вовсе.

- `role:u8` в `AUTH_OK` — enum расширяется без слома формата.
- `transfer_id` в передачах — параллельные и восстановимые передачи.
- Код ошибки `QUOTA_EXCEEDED` зарезервирован.
- VFS — единственная точка резолва путей: подмена «один корень» → «виртуальные
  маунты по пользователю» локализована в одном классе.
- `SUBSCRIBE`/`EVENT_FS` уже фильтруются по видимости сессии (в v2.0 видимость у
  всех одинаковая, но фильтр — в сигнатуре EventBus с первого дня).
